# AI 드론 비전 추적 시스템 설계서

버전: v1.1 · 기준일: 2026-10-04 · 상태: 개발 기준선 / 실물 검증 전

하드웨어 고정 · 실내 단일 지정 드론 · 카메라 추종 MVP · GitHub + Codex

## 01. 프로젝트 정의와 범위

### MVP 정의
실내의 사전 정의된 시험 영역에서 지정 드론 1대를 단일 USB 카메라 영상으로 실시간 검출·추적하고, 검증된 팬·틸트 운용 범위 안에서 드론이 화면 중앙의 기준점 부근에 유지되도록 제어한다. 관측 소실·영상 지연·통신 장애·명령 범위 제한 시 정해진 제한 및 정지 동작을 수행한다.

**최종 지향점과 MVP를 구분한다.** 카메라와 지시 장치가 함께 따라가는 모습이 최종 아이디어이지만, v1.0의 완료 조건은 영상 십자선과 카메라 자동 추종이다. 레이저/LED 지시는 후속 범위이며 이번 설계에 레이저 구동, 자동 조사 또는 정밀 조준 구현을 포함하지 않는다.

### 확정한 범위
| 항목 | 기준 |
|---|---|
| 대상 | 팀이 지정한 드론 1종, 화면에서 운용하는 드론 1대 |
| 환경 | 실내, 시험자가 관리하는 한정된 공간 |
| 검출 클래스 | `drone` 한 개 |
| 연산 | 노트북에서 영상 처리·AI 추론·카메라 제어 계산 |
| 구동 | Uno R3 → PCA9685 → MG996R 두 개 |
| 하드웨어 | 첨부 최종 구매 목록 유지. 임의 교체·추가 구매 금지 |
| 개발 방식 | GitHub 관리, Codex 구현 + 별도 Codex 리뷰 |

### MVP 포함 / 제외
포함: 영상·웹캠·실물 카메라 입력, 지정 드론 검출, ID 연결, 화면 기준 오차, 팬·틸트 추종, 일시적 소실 처리, 정지, 실행 로그, 재현 가능한 시험.

제외: 모든 드론 종류 인식, 같은 모델 기체의 개체 신원 구별, 여러 드론 동시 추종, 실외 장거리 추적, 3차원 위치·거리 추정, 360도 자동 수색, 드론 비행 제어, 레이저 자동 조사, 충돌·요격 기능.

v1.1 재확인: 단안/마커/스테레오/깊이 모델 거리 측정, 두 번째 카메라, 3축 이상, 추가 전원,
무제한 회전과 머리 위·후방 모든 경로의 무중단 추종을 추가하지 않는다. 자동 180도 뒤집기나
미래 확장을 위한 프레임워크도 만들지 않는다. [운용 범위 상세](07_single_camera_operating_envelope.md)를 따른다.

### 문서의 상태
v1.1은 개발 기준선이며 성능 검증 완료 보고서가 아니다. ‘확정’은 팀이 채택한 방향, ‘초기값’은 시험용 제안, ‘실측’은 장비 수령 후 채울 값이다. 기능·성능·실물 배선 검증은 아직 수행하지 않았다.

## 02. 시스템 구조와 역할

### 데이터 흐름
```text
USB 카메라 → 노트북 영상 입력 → 드론 검출·ID 추적
                                ↓
                    드론 중심과 화면 중앙의 오차
                                ↓
                    카메라 팬·틸트 목표값 계산
                                ↓ USB Serial
                         Arduino Uno R3
                                ↓ I²C
                            PCA9685
                                ↓ PWM
                         팬 / 틸트 서보
                                ↓
                      카메라 방향 변경 → 새 영상
```
화면에서 얻은 오차로 카메라 방향을 바꾸고 새 영상으로 결과를 확인하는 폐루프다. 노트북이 인식과 제어 계산을 하고, Arduino는 명령 검사·각도 제한·서보 신호 생성 지시·통신 감시를 담당한다.

### 소프트웨어 모듈 경계
| 모듈 | 입력 → 출력 / 책임 |
|---|---|
| capture | 영상 소스 → frame_id, 단조 시각, 원본 크기, BGR 영상 |
| perception | 최신 프레임 → bbox, confidence, track_id, 관측 여부 |
| target_manager | 검출 결과 → 단일 활성 대상과 마지막 관측 시각 |
| state_machine | 관측·오류·사용자 입력 → SEARCH / ACQUIRE / TRACK 등 |
| controller | 대상 중심·기준점·dt → 제한된 카메라 목표 명령 |
| transport | 명령 → USB Serial 송신·ACK 수신·장애 상태 |
| firmware | 검증한 명령 → PWM 출력, 자체 제한·watchdog |
| overlay / logger | 영상 표시와 재현 가능한 실행 기록 |

### 구현 원칙
영상 입력, 인식, 제어, 통신을 서로 교체할 수 있게 분리한다. 초기에는 실제 통신 대신 MockTransport를 사용한다. 오래된 프레임을 순서대로 처리해 지연을 누적하지 않고, 실시간 입력에서는 가장 최근의 프레임을 우선 처리한다.

녹화 영상은 순차 재생 평가와 실시간 모의 실행을 구분한다. 영상 파일의 시간과 실제 벽시계 시간을 혼용하지 않는다. 새로운 영상·카메라 재연결 때에는 기존 추적 상태를 초기화한다.

### 하드웨어 고정과 조립 완료는 다르다
기존 부품을 유지하되, 사진만으로 호환·체결·전류 용량을 확정하지 않는다. M/M 점퍼의 결합, 2.5sq 단자와 0.75SQ 전선의 적합성, U 브라켓의 축 지지·서보 혼·나사, 카메라 장착점, USB 케이블을 실물에서 확인한다. 부적합 부품을 억지로 결합하지 않는다. 추가 부자재가 꼭 필요하면 먼저 기록하고 사용자 승인을 받는다.

MG996R은 ‘호환품’이다. 정품 사양의 토크·정지전류·회전각을 그대로 보장값으로 사용하지 않는다. 카메라·브라켓 무게와 케이블 당김, 무게중심을 포함해 시험한다. 정지 토크만으로 연속 추종 성능을 보장하지 않는다.

## 04. 전원·배선과 기구 안전

### 연결 원칙
| 출발 | 도착 | 구분 |
|---|---|---|
| 노트북 USB | 카메라 | 영상 + 카메라 전원 |
| 노트북 USB | Arduino | 통신 + 보드 전원 |
| Arduino 5V | PCA9685 VCC | 로직 전원, 서보 전원 아님 |
| Arduino SDA / SCL | PCA9685 SDA / SCL | I²C 신호 |
| Arduino GND | PCA9685 GND | 공통 기준 전압 |
| 외부 어댑터 +5V | PCA9685 서보 V+ | 서보 전원 |
| 외부 어댑터 − | PCA9685 GND | 서보 전류 귀환·공통 GND |
| PCA 채널 0 / 1 | 팬 / 틸트 서보 | S / V+ / GND 극성 확인 |

공통 GND는 Arduino와 서보 신호가 같은 0V 기준을 보도록 하는 연결이다. **두 전원의 +5V를 서로 묶는다는 뜻이 아니다.** USB로 Arduino에 전원을 줄 때 어댑터 +5V를 Arduino 5V 핀에 연결하지 않는다. 서보 전류가 Arduino나 브레드보드 전원 레일을 통과하지 않게 한다. [S2]

PCA9685의 로직 전원과 서보 전원은 구분한다. Adafruit 자료는 전원 구조를 이해하기 위한 참고이며, 선택한 VLT-MD032 보드의 보호회로·실크·커넥터 방향이 동일하다고 가정하지 않는다. [S2]

### 조립·시운전 순서
전원을 모두 분리한 상태에서 극성·체결을 검사한다. 로직 통신만 확인한 뒤, 기구부를 지지한 상태에서 한 축씩 저속 시험한다. 끝단을 무리하게 밀지 않고 축별 중립·최소·최대·방향을 기록한다. 두 축 통합 뒤 케이블 당김, 프레임 간섭, 전압 강하, 보드 재시작, 발열을 확인한다.

50Hz는 서보 PWM의 시험 시작 후보일 뿐 최종 보장값이 아니다. 펄스폭·기구 각도 변환은 실측 보정값으로 제한한다. 0~180도 전 구간을 처음부터 자동 순회하지 않는다.

축별 보정 범위와 별도로 케이블·간섭·속도를 반영한 보수적 운용 범위를 확인한다.
각 축이 따로 안전해도 2축 조합이 안전하다고 가정하지 않는다. 조합 범위가 미확인인 경우
실물 구동 미검증 상태로 두며 숫자나 금지 영역을 임의 생성하지 않는다.

### 정지의 의미
소프트웨어 정지는 새 이동 명령을 멈추고 마지막 출력 명령을 유지하는 동작이다. 물리적인 순간 정지나 전원 차단을 보장하지 않는다. 전원을 끄면 틸트축이 처질 수 있으므로 기구부를 지지한다. USB만 뽑아도 외부 서보 전원은 남을 수 있다. 시험자는 접근 가능한 DC 전원 분리 지점을 확보하고 완제품 AC 어댑터를 분해하거나 노출 AC 배선을 만들지 않는다.

## 05. 영상·검출·추적 설계

### 영상 입력
목표 입력 모드는 1920×1080 / 60FPS이다. 제조사 자료에 1080p 60FPS가 안내되지만 실제 FPS는 USB·노트북·소프트웨어 조건에 영향을 받는다. 이 숫자를 AI 처리 FPS나 지연시간으로 대신 보고하지 않는다. [S1]

원본 해상도, 실제 프레임 간격, 포맷, 노출 설정을 기록한다. USB3 직결로 시험하고 불안정하면 동일 카메라에서 1080p 30FPS 또는 낮은 해상도를 비교한다. 이는 하드웨어 변경이 아니라 운용 설정 변경이다. 노출·흔들림·지연을 각각 시험하며 60FPS라는 이유만으로 움직임 품질을 보장하지 않는다.

### 검출 모델
YOLO 계열 경량 모델의 전이학습을 시작점으로 한다. 정확한 모델 세대·패키지 버전·GPU 백엔드는 노트북 환경 확인 후 고정한다. 이전 대화의 특정 모델명은 후보이며 최신 버전이라는 이유만으로 자동 교체하지 않는다.

사전학습 가중치가 지정 드론을 이미 인식한다고 가정하지 않는다. 학습 후 클래스 이름이 `drone`인지 검증한다. 초기 입력 크기 640을 기준으로, 작은 드론이 잘 안 잡힐 때 960 등과 속도·정확도를 비교한다. 데이터셋·가중치·설정 버전을 함께 기록한다.

### 추적 방식
각 처리 프레임에서 검출하고 BoT-SORT로 프레임 사이 ID를 연결한다. 구현 시 tracker를 명시하고 기본값에 의존하지 않는다. BoT-SORT는 카메라 움직임 보정과 선택적 ReID를 제공한다. 초기에는 ReID를 끄고, 필요할 때 ByteTrack과 비교한다. 움직임 보정이 모든 배경에서 더 좋다는 가정은 하지 않는다. [S3]

검출을 한 번만 수행하고 추적기가 계속 정답 위치를 제공하는 구조가 아니다. 관측 누락 시 예측 ID나 예측 박스가 있다는 이유로 새 이동을 계속 지시하지 않는다. ‘최근 실제 검출’과 ‘추적기 예측’을 인터페이스에서 구별한다.

### 좌표와 대상 관리
원본 영상 기준 `bbox=(x1,y1,x2,y2)`와 중심을 사용한다. 리사이즈·레터박스 좌표가 전달되면 원본으로 복원하고 중복 변환하지 않는다. 유효한 기존 대상을 우선 유지하며 단일 대상 운용 중 여러 후보가 나와도 매 프레임 가장 큰 박스로 전환하지 않는다. 장기 소실 후에는 새 획득 절차를 거친다. 같은 모델 기체의 물리적 신원을 보장하지 않는다.

## 06. 카메라 추종 제어와 상태

### 카메라 중심 오차
원본 크기를 W×H, 드론 중심을 (cx, cy)로 두고 화면 중앙을 기준점으로 사용한다. 정규화 오차는 `ex=(cx-W/2)/(W/2)`, `ey=(cy-H/2)/(H/2)`다. 부호는 영상에서 오른쪽·아래쪽이 양수이며 실제 서보 회전 부호는 축별 실측으로 연결한다.

제어는 Dead Zone + P 방식으로 시작한다. P 출력은 제한된 카메라 이동 속도로 해석하고 실제 dt를 이용해 목표 명령을 갱신한다. 적분항은 사용하지 않는다. 진동이 남을 때만 필터링한 PD를 비교한다. 센터 오차, 최대 속도, 목표값 변화율, 기구 각도 범위를 함께 제한한다.

MVP에서는 px 오차를 카메라의 정확한 각도로 직접 등치하지 않는다. 새 관측이 없거나 너무 오래된 프레임이면 더 움직이지 않는다. 서보의 ACK와 마지막 명령값은 실제 측정 각도가 아니다.

거리 입력 없이 영상 중심 오차로 제어하며 bbox 크기를 검증 없이 m로 변환하지 않는다.
촬영/평가용 사람이 잰 거리는 시험 조건이지 시스템의 실시간 거리 출력이 아니다.

### 명령 제한과 안쪽 복귀
호스트는 허용 범위로 제한하며 바깥 오차가 지속돼도 내부 목표/속도 상태가 누적되지 않게 한다.
펌웨어의 범위 밖 SET 거부도 유지한다. 유효 검출과 명령 제한은 동시에 존재할 수 있으므로
`control_saturated` 같은 진단으로 기록하고 관측 소실과 구분한다. 상태 추가는 필수가 아니다.
새 유효 관측이 안전한 안쪽 복귀를 요구하면 구동 허가·속도·변화율 제한을 지키며 복귀한다.
경계 진동의 유지 시간/히스테리시스는 모의시험 후 실물에서 정하며 값을 미리 측정값으로 만들지 않는다.
명령 포화는 물리적 스톨·끝단 도달·머리 위 위치 감지가 아니며 실제 위치 센서 출력으로 표시하지 않는다.

### 상태별 동작
| 상태 | 조건 / 행동 |
|---|---|
| INIT | 설정·모델·통신 검사. 보정 미완료 시 실물 구동 차단 |
| SEARCH | 현재 방향에서 검출. 자동 좌우 스캔 없음 |
| ACQUIRE | 일관된 후보를 짧게 재확인. 아직 자동 이동하지 않음 |
| TRACK | 최근 실제 관측만으로 카메라 추종 |
| LOST | 첫 관측 누락부터 새 이동 중단. 마지막 명령 유지 |
| PAUSED | 사용자가 일시정지. 재개는 명시적 조작 |
| FAULT | 카메라·통신·설정 이상. 구동 해제 상태로 전환 |

### 초기 시간 기준
후보 확인은 3개 처리 프레임과 최대 0.5초를 초기값으로 한다. 일시적 소실은 최대 0.5초 동안 같은 후보를 다시 확인하고, 2초 이상 관측이 없으면 ID를 해제하고 SEARCH로 돌아간다. 이 시간은 실험으로 조정할 제안값이며 시험 결과가 아니다.

SEARCH는 카메라가 보는 범위에서만 재검출한다. 시야 밖의 드론을 자동으로 찾는 기능은 MVP에 없다. 정상 재획득 시에도 급격히 다른 방향으로 전환하지 않는다. 카메라 재연결·시리얼 재연결 뒤에는 자동 구동을 재개하지 않는다.

LOST/HOLD는 마지막 출력 명령 유지이며 이전 목표로 계속 접근하는 램프 진행과 다르다.
현재 시야의 새 실제 관측으로 기존 획득 절차를 다시 거쳐야 한다. 자동 좌우 반전이나 뒤집기를 하지 않는다.

### 실물 구동 허용 조건
설정의 hardware_enabled, 완료된 축별 보정, 정상 통신 확인, 현장 운영자의 명시적 ARM이 모두 필요하다. 기본 패키지의 실물 구동은 꺼져 있다. 모의 실행을 실제 서보 시험 통과로 간주하지 않는다.

## 07. 노트북–Arduino 통신 계약

### 기본 방식
USB Serial, 115200bps, 8N1, ASCII 한 줄 메시지, LF 종료를 초기 설계로 한다. CRLF도 수신 측에서 허용한다. 실제 구현 세부 사항은 `02_serial_protocol.md`를 따른다. 본 프로토콜은 프로젝트 제안이며 제조사 표준이 아니다.

| 명령 | 의미 |
|---|---|
| HELLO / READY | 프로토콜 버전·현재 세션 확인, 자동 구동하지 않음 |
| ARM | 보정과 운영자 확인 후 이동 명령 수신 허용 |
| SET | 팬·틸트 목표값. 누적 델타가 아닌 절대 명령값 |
| HOLD | 진행 중 목표 갱신을 취소하고 마지막 출력 명령 유지 |
| DISARM | HOLD 후 새 SET 수락 금지. 전원 차단과 다름 |
| PING | 연결 상태 확인. 구동 허가·관측 유효성을 갱신하지 않음 |
| ACK / ERR | 명령 처리 결과. 실제 축 도달 확인이 아님 |

초기 송신 빈도는 최대 20Hz, 통신 watchdog은 500ms다. Arduino는 호스트와 별도로 범위·형식·세션·순서를 검사하고 내부 속도 제한을 적용한다. 범위를 벗어난 값, 비정수, 지나치게 긴 줄, 잘못된 세션, 역순 명령을 거부한다.

### 통신 장애와 오래된 명령
호스트는 ACK가 지연되면 명령을 계속 쌓지 않는다. 전송 큐는 최신 목표 중심으로 제한한다. Arduino는 유효한 제어 갱신이 끊기면 HOLD 후 재ARM을 요구한다. 통신·프로세스가 복구되어도 자동으로 움직이지 않는다. 잘못된 데이터나 PING으로 watchdog을 계속 연장하지 않는다.

이전 세션의 명령이 새 실행에 섞이지 않도록 세션 토큰을 포함한다. 같은 명령 재전송은 추가 이동을 만들지 않아야 한다. 프로토콜 시험에는 부분 수신, 줄 합쳐짐, 버퍼 초과, 중복, 연결 끊김을 포함한다.

### 피드백의 한계
현재 구성에는 외부 각도 센서가 없다. `last_command`는 명령한 위치를 뜻하며 실제 카메라 각도가 아니다. 위치 성능은 영상상의 중심 오차와 별도 관측으로 평가한다. ACK만으로 물리적인 정지·정확한 도달·기구 안전을 증명할 수 없다.

## 08. 학습 데이터 구성

### 시작 규모
지정 드론이 있는 이미지 약 900장과 없는 배경 약 100장, 총 1,000장을 1차 운영 목표로 한다. 600~800장으로 먼저 학습해도 되며 실패 조건을 300~500장씩 보강한다. 이 수량은 팀의 작업 시작점이지 성능 보장 최소량이 아니다. [U2]

### 촬영과 추출
20~25개 안팎의 20~40초 영상을 조건을 바꿔 촬영한다. 처음에는 0.5~0.8초 간격으로 프레임을 추출하고 중복·과도한 흐림·빈 프레임을 검토한다. ‘20개 × 30초 ÷ 0.5초 = 1,200프레임’은 추출 전 후보 수다. 최종 채택 수와 다르다.

방향, 거리, 높이, 배경, 조명, 이동 방향을 섞는다. 실제 드론과 실제 카메라 조건을 우선한다. 가까운 거리 25%, 중간 40%, 먼 거리 35%는 드론 포함 이미지에 적용하는 초기 촬영 배분 예시다. m 단위 거리는 시험 공간에서 결정하고 실제 bbox 크기도 기록한다.

학습 초기에는 프로펠러를 분리한 정지 기체로 외형 촬영이 가능하지만 그것만으로 비행 상태를 대표하지 않는다. 회전하는 프로펠러를 손으로 잡고 촬영하지 않는다. 비행 촬영은 장소 규정과 지도자의 감독 아래 수행한다.

### 라벨과 분할
`drone` 한 클래스로 보이는 기체 전체를 일관되게 박스로 표시한다. 그림자·사람·지지대를 포함하지 않는다. 객체 경계를 판단하기 어려운 영상은 검토 대상으로 분리한다. 배경 이미지는 실제로 드론이 없는 경우만 사용한다.

원본 영상보다 더 넓은 촬영 세션 단위로 train / validation / test를 먼저 나눈다. 같은 촬영을 잘라 만든 파일도 같은 그룹에 넣는다. 대략 70 / 20 / 10을 목표로 하되 그룹 독립성을 우선한다. 증강·중복 제거·자동 라벨링을 포함한 모든 파생 파일은 원본 split을 계승한다. 검증·시험 데이터가 학습 데이터에 섞이면 수치를 신뢰할 수 없다. [S4]

처음 100~200장을 사람이 라벨링하고 초기 모델로 나머지 라벨 초안을 만든 뒤 사람이 수정한다. test는 최종 평가 전까지 잠근다. 반복 개선에 사용한 test는 이후 validation으로 전환하고 새 test 세션을 확보한다.

## 09. 시험과 MVP 완료 기준

### 기능 완료 조건
새 시험 영상에서 지정 드론을 검출·ID 연결하고, 실물 카메라가 두 축으로 추종해야 한다. 대상 소실, 정지 요청, 카메라 오류, 통신 끊김에 대한 정해진 동작을 재현해야 한다. 재실행에 필요한 코드 버전·설정·모델·시험 기록을 남긴다.

### 초기 정량 목표 — 아직 미측정
| 지표 | v1.0 시험 목표 / 측정 범위 |
|---|---|
| 처리 속도 | 실제 노트북에서 20FPS 이상. 입력 FPS와 별도 기록 |
| 호스트 처리 지연 | 프레임 수신 완료→명령 enqueue p95 100ms 이하 |
| 카메라 중심 유지율 | 유효 가시 구간의 80% 이상에서 중앙 허용 영역 유지 |
| 최초 획득 | 가시 조건 충족 후 1초 이내, 예시 시험 10회 중 8회 |
| 시야 내 재획득 | 다시 보인 후 2초 이내, 예시 시험 10회 중 8회 |
| 통신 장애 처리 | 마지막 유효 제어 갱신 후 500ms + 최대 1회 펌웨어 tick 이내 HOLD·구동 잠금 |

중앙 허용 영역은 초기값으로 수평 오차 ≤ 화면 너비의 5%, 수직 오차 ≤ 높이의 5%다. 예를 들어 1920×1080이면 각각 96px, 54px다. 이는 제어기의 Dead Zone과 다른 평가 기준이다.

가시 구간은 ‘모델이 검출한 프레임’이 아니라 시험자가 정한 실제 드론 가시 구간이다. 최초·재진입 후 고정 1초의 정착 구간을 제외하고 나머지 가시 시간 전체를 분모로 한다. 검출 실패·프레임 드롭·추종 실패는 성공 시간으로 세지 않는다. 처리된 프레임만 보고 유지율을 부풀리지 않는다.

### 따로 기록할 것
검출은 Precision, Recall, mAP50, mAP50–95와 작은 기체의 실패 사례를 보고한다. 지연은 프레임 수신 이후의 호스트 지연과 Serial ACK 왕복을 분리한다. 카메라 센서 노출부터 실제 축 움직임까지의 전체 지연은 별도 실험 없이는 측정했다고 쓰지 않는다. FPS 또는 ACK로 이를 대신하지 않는다.

### 시험 장면
정지 기체, 저속 수평 이동, 수직 이동, 거리 변화, 배경 변화, 잠깐 가림, 시야 이탈·재진입, 드론 없는 장면, PC 프로그램 중단, USB 분리·재연결을 시험한다. 초기 공간·거리·속도·조명 조건을 고정하여 기록하고 통합 시험 전 기준값을 동결한다. 기준을 바꾸면 이유와 이전 결과도 남긴다.

기구/명령 허용 범위, 시험 영역, 현재 시야를 구분한다. 카메라는 경로 옆에 두고 앞쪽의
제한 영역부터 시험하며 머리 위·후방 무중단 추종을 필수 성공 기준에 추가하지 않는다.
동결한 영역 내 놓침·프레임 드롭·추종 실패를 사후에 영역 밖으로 재분류하지 않는다.
계획된 영역 밖 시험은 별도의 제한동작 시험이다. HOLD 성공을 추종 성공으로 집계하지 않는다.
기존 정량 목표·가시 시간 분모는 유지한다. [SC01–SC08](07_single_camera_operating_envelope.md)의
모의 회귀시험은 관련 런타임 구현 시 연결하며 현재 문서/설정 CI 통과와 구분한다.

## 10. 개발 단계와 병렬 작업

### 단계별 산출물
| 단계 | 작업 | 완료 증거 |
|---|---|---|
| P0 | 저장소·노트북 환경 확인, 환경 버전 결정 | 환경 기록, 설치 계획, 첫 작업 범위 |
| P1 | 영상 입력·오버레이·프레임 시각 | 녹화 영상 정상 종료, 예외 처리 시험 |
| P2 | 데이터 분할·라벨·학습·고정 시험 | 데이터 manifest, 모델 카드, 평가 결과 |
| P3 | 검출·추적·대상 선택·상태 | 새 영상 검출, 소실·재획득 테스트 |
| P4 | 가상 카메라 제어·Mock 통신 | 부호·dt·제한·정지 회귀시험 |
| P5 | Arduino 통신·실물 축 보정 | 감독하의 통신·한 축·두 축 시험 기록 |
| P6 | 카메라 통합·튜닝·완료 평가 | 반복 가능한 시연과 성능·실패 보고 |

하드웨어 도착 전 P0~P4의 구조·모의 시험을 진행할 수 있다. 단, 지정 드론의 실제 학습·검증 완료는 적절한 실제 데이터가 있어야 한다. 공개 영상이나 임시 가중치로 파이프라인을 시험한 것을 지정 드론 인식 완성으로 표시하지 않는다.

### 역할 분리
비전 담당: 입력·데이터·검출·추적·평가. 제어 담당: 시리얼 계약·펌웨어·배선·기구·실물 시험. 통합 담당: 인터페이스·설정·상태·로그·PR 관리. 개인 이름·마감일은 여기서 임의 지정하지 않는다.

하나의 PR은 하나의 검증 가능한 목표로 제한한다. 인터페이스 변경은 생산자와 소비자, 문서, 테스트를 함께 갱신한다. 비전 팀은 FakeDetection을, 펌웨어 팀은 수동 명령 시험을 이용해 서로를 기다리지 않고 진행한다.

### 첫 구현 작업
P0에서 OS, Python, GPU 종류·VRAM, 드라이버와 사용 가능한 백엔드를 확인한다. CUDA는 NVIDIA 환경에서만 후보로 검토하고 GPU가 없으면 CPU로 기능 검증을 시작한다. 현재 ZIP은 환경을 조사하거나 설치한 결과물이 아니다. 노트북 확인 후 호환되는 의존성을 고정하고 lockfile·설치 재현 절차를 추가한다.

## 11. 결정 기록과 변경 규칙

### 지금 고정한 것
대상·실내 범위·기존 하드웨어, 노트북 영상 처리, USB Serial, Uno/PCA9685 서보 제어, 영상 중앙 기준, 단일 대상, 초기 고정 시야 탐색, Codex 구현/리뷰 분리, 실제 구동 기본 꺼짐을 고정한다.

### 초기 제안값과 실측 보류값
| 항목 | 상태 / 처리 |
|---|---|
| 영상 1080p / 60FPS | 목표값. 실제 협상 결과와 실측 FPS 기록 |
| 경량 YOLO + BoT-SORT | 초기 방향. 모델/라이브러리 버전은 환경 확인 후 고정 |
| 입력 크기 640, ReID 꺼짐 | 초기 비교 기준. validation 성능과 지연으로 조정 |
| Serial 20Hz / watchdog 500ms | 초기값. 시험·프로토콜 변경 기록 필요 |
| 실제 각도·PWM·방향·속도·P/PD 계수 | 실측 전 null. 미설정 상태로 실물 구동 금지 |
| 시험 거리·속도·조명·bbox 크기 | 공간·데이터 확보 후 정하고 통합 평가 전 동결 |
| GPU·OS·패키지 버전 | 사용자 노트북에서 확인 |
| 라이선스·데이터 공개 범위 | 저장소 공개·재배포 전에 결정 |
| Codex 설치·플러그인·MCP·자동 리뷰 연결 | D18/D19와 현재 자동화 상태를 적용. 초기 v1.0 미정 문구로 승인된 구축을 되돌리지 않음 |

### 기존 논의의 보완 사항
단일 화면 기준점 보정만으로 거리가 달라지는 물체의 레이저 일치를 보장할 수 없다. 따라서 이번 완료 기준에 레이저 정확도를 넣지 않는다. 5V 6A 표기만으로 서보 두 개의 모든 동작 조건을 보장하지 않는다. 카메라 60FPS와 AI 60FPS, 검출 정확도와 모터 추종 정확도는 각각 별도다.

### 변경 절차
범위·하드웨어·비용·외부 업로드·모터 자동 가동·라이선스 변경은 사용자 승인이 필요하다. 실험 수치는 validation과 실물 결과로 변경하되, `05_decisions.md`와 해당 설정을 함께 갱신한다. test를 반복 튜닝에 사용하지 않는다.

문서 간 충돌이 생기면 최신 승인 결정 기록 → 본 설계 → 세부 규격 → 예제 설정 순으로 확인한다. 코드만 조용히 바꿔 불일치를 남기지 않는다. Markdown이 편집 원본이고 DOCX는 v1.0 읽기용 스냅샷이다.

## 12. Codex 작업과 전달 기준

### 이번에 준비한 것
저장소 루트의 `AGENTS.md`에 공통 작업 규칙과 리뷰 규칙을 둔다. OpenAI는 Codex의 저장소 지침 파일로 AGENTS.md를 문서화한다. 이 파일을 제공하는 것과 Codex 설치·계정 연결·자동 리뷰 활성화는 별개다. [S5]

`prompts/implementation.md`, `prompts/review.md`, `prompts/handoff.md`는 각각 구현, 분리된 리뷰, 작업 인수인계에 사용한다. 작성자와 리뷰어 모두 Codex를 쓰되, 리뷰는 변경 커밋과 요구사항을 받아 새 작업에서 수행하도록 설계한다.

### 작업 흐름
사용자 작업 선택 → Codex 구현 → 로컬/CI 검증 → 별도 Codex 리뷰 → 허용된 횟수의 수정·재검증.
이후 진행/병합 조건은 D18/D19와 [자동화 상태](automation/setup-status.md)를 따른다.

리뷰는 실제 diff와 주변 코드를 확인하고 파일·위치·재현 조건·영향을 보고한다. 같은 모델을 두 번 사용한다고 독립 검증이 보장되는 것은 아니므로 결정적 테스트와 사람이 확인하는 실물 시험을 병행한다. 무제한 수정 반복·추가 비용은 허용하지 않으며 자동 병합은 별도 단계 검증 전까지 비활성이다.

### 완료 보고 형식
변경 내용, 요구사항 ID, 실행한 테스트와 결과, 실행하지 못한 시험, 실물 영향, 남은 위험, 다음 한 가지 작업을 기록한다. 무실행 코드를 실행 성공으로, 모의 통신을 실물 통신으로, 문서 검사 통과를 프로젝트 성능 검증으로 표현하지 않는다.

### 저장소 포함 / 제외
포함: 설계 원본, DOCX 스냅샷, 시리얼 규격, 데이터·평가 계획, 단계별 할 일, 안전한 예제 설정, 기록 양식, AGENTS.md, 프롬프트, PR·작업 템플릿, 패키지 검사 스크립트.

제외: 촬영 영상·라벨·학습 가중치·API 키·계정 로그인 등 로컬 자료. 추종 런타임과 실제 Arduino
펌웨어는 아직 구현 전이다. 자동화 도구의 실제 구현 상태는 자동화 상태 문서를 확인한다.
