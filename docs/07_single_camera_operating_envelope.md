# 단일 카메라·2축 MVP: 운용 한계 · v1.1

상태: 2026-10-04 사용자 요청으로 현재 저장소에 반영한 설계 기준. 런타임 구현·실물 시험 전.

## 1. 근거와 기존 설계에서 확인된 내용

첨부 v1.0 ZIP의 `docs/01_system_design.md`와 `docs/05_decisions.md`를 기준으로 확인했다. 다음 내용은 이번에 새로 요구하는 기능이 아니다.

| 기존 위치 | 이미 포함된 내용 |
|---|---|
| 설계 01장 | 단일 지정 드론, 카메라 추종 MVP, 3차원 위치·거리 추정 및 360도 자동 수색 제외 |
| 설계 04장 | 서보 범위·방향 실측, 전압 강하·리셋·기구 간섭 확인, 무조건 0~180도 순회 금지 |
| 설계 05장 | 1080p60은 입력 목표, 실제 FPS·노출·처리 지연 별도 확인 |
| 설계 06장 | 새 관측 없으면 이동 갱신 중단, SEARCH는 현재 시야에 한정, 실측 보정 전 구동 차단 |
| 설계 07장 | ACK·명령값은 실제 각도 측정이 아님, HOLD/DISARM/watchdog 계약 |
| 설계 09장 | 시험 거리·속도·조명 조건 사전 정의, 가시 시간 기준 평가와 실패 기록 |
| 설계 11장 | 단일 기준점으로 모든 거리의 레이저 일치 보장 불가, 5V6A 표기만으로 구동 보장 불가 |

따라서 본 보완의 목적은 **확장 기능 구현이 아니라 기존 범위와 경계 동작을 더 명확히 하는 것**이다. 최신 저장소에 이미 반영된 내용은 중복 구현하지 않는다.

## 2. 유지할 하드웨어와 MVP

하드웨어: U30CAM IMX415 USB 카메라 1대, MG996R 호환 서보 2개, Arduino Uno R3, PCA9685 1개, 기존 5V 6A 어댑터와 선정된 기구·배선 부품.

### 확정 MVP 정의

실내의 사전에 정한 시험 영역에서 지정 드론 1대를 단일 USB 카메라로 검출·추적하고, 검증된 팬·틸트 운용 범위 안에서 카메라가 드론을 화면 중앙 부근에 유지하도록 제어한다. 관측 소실·영상 지연·통신 장애·명령 범위 제한 상황에서는 정해진 제한 및 정지 동작을 수행한다.

시스템은 드론을 조종하지 않고 카메라만 움직인다. 화면 중앙 추종은 영상상 위치 오차를 이용하며 실제 미터 단위 거리를 입력으로 요구하지 않도록 유지한다.

### 현재 제외 / 후속 검토

거리 측정(단안 추정·마커·스테레오·깊이 모델 모두), 실내 3D 좌표 궤적, 두 번째 카메라, 3축 이상, 무제한 회전, 시야 밖 자동 탐색, 머리 위에서 뒤쪽까지 모든 경로의 무중단 추종 보장, 레이저 자동 지시·정밀 조준.

원래 모듈 경계(capture/perception/controller/transport)는 유지하되 미래의 스테레오나 다축 기능을 위한 프레임워크·패키지·가짜 데이터 생산 코드를 지금 추가하지 않는다.

## 3. 거리 고민을 반영하는 방법

거리 측정 부재는 이번 MVP의 결함이 아니다. 실제 거리 값을 만들지 않으며, 바운딩 박스 크기를 검증 없이 미터로 변환하지 않는다. 이미 거리 필드가 있다면 의미를 점검하고 미지원/미측정을 명확히 표시한다. 필드 자체가 필요 없으면 새로 만들지 않는다.

촬영·평가용 사람이 잰 거리는 여전히 기록한다. 이것은 시스템의 실시간 거리 출력이 아니라 시험 조건이다. 가까움·멀어짐으로 바뀌는 드론의 영상 크기에 대한 검출·추종 성능은 기존 계획대로 평가한다.

외부 참고: OpenCV의 투영 모델은 3D 점을 2D 영상으로 투영한다. 알려진 3D 점과 대응 영상점·카메라 보정을 사용하는 PnP는 별도 위치 추정 문제다. 한 대이므로 어떤 조건에서도 거리를 알 수 없다는 표현도, 현재 검출 박스만으로 실제 거리가 측정됐다는 표현도 사용하지 않는다.

## 4. 머리 위 통과와 운용 영역

카메라를 시험 경로 옆에 배치하고 앞쪽의 제한된 영역부터 시연한다. 머리 위·후방 연속 통과를 필수 성공조건으로 추가하지 않는다. 정확한 범위는 실물 조립 후 정하며 특정 90도 또는 180도를 보장값으로 사용하지 않는다.

다음을 구분한다.

- **기구·명령 허용 범위:** 축 방향, 최소/중립/최대, 케이블 여유, 간섭, 속도 제한을 실제로 확인해 정한다.
- **시험 영역:** 위치·거리·높이·경로·조명을 시험 전에 정한다. 실제 거리·높이는 사람이 정한 조건이다.
- **카메라의 현재 시야:** 드론이 보이는 구간. 여기서 사라지면 기존 LOST/SEARCH 규칙을 따른다.

명령상의 서보 각도와 실제 지평선 기준 카메라 각도는 같다고 가정하지 않는다. 외부 위치 피드백이 없는 현재 구성에서 “드론이 머리 바로 위에 있음” 또는 “실제 축이 끝단에 도달함”을 정확히 측정했다고 보고하지 않는다.

팬과 틸트의 개별 범위가 각각 안전해도 조합에서 간섭할 수 있으므로 보수적인 2축 허용 영역을 실물로 확인한다. 이를 확인하지 못하면 실물 구동은 미검증 상태로 둔다. 머리 위 추적 문제를 해결한다는 이유로 자동 좌우 반전, 급격한 180도 회전, 자동 뒤집기 동작을 추가하지 않는다.

## 5. 경계에서의 소프트웨어 동작 보완

### 5.1 유효 관측이 있고 명령 범위 안인 경우

기존 P + Dead Zone, dt·속도·변화율 제한을 유지한다. 좌표는 기존 영상 좌표계와 축별 실측 방향을 따른다.

### 5.2 목표 명령이 제한에 걸리는 경우

호스트에서는 허용 범위로 제한하고, 그 바깥 방향으로 내부 목표값이나 속도 상태가 계속 쌓이지 않도록 한다. 펌웨어는 기존 계약대로 잘못된 범위의 SET을 거부한다. 두 계층의 보호를 모두 유지한다.

관측이 유효해도 명령이 제한될 수 있다. 이 상황을 검출 소실과 혼동하지 말고 `control_saturated`처럼 기존 구조에 맞는 진단값으로 기록한다. 새로운 전체 상태머신 상태를 반드시 만들 필요는 없다.

제한 바깥으로 더 움직이지 않되, 새로운 유효 관측이 안전한 안쪽 복귀를 요구하면 기존 구동 허가와 제한을 지키며 복귀할 수 있어야 한다. 순간 경계 통과가 진동을 만들지 않도록 필요한 유지 시간·히스테리시스는 모의시험 후 실물에서 정한다. 숫자를 사실처럼 만들어 넣지 않는다.

명령 제한 신호는 **물리적 모터 스톨 감지나 실제 위치 센서 출력이 아니다.** 이를 이용해 “자동으로 머리 위 통과를 해결함”이라고 보고하지 않는다.

### 5.3 관측 소실·오래된 프레임

원래 LOST/HOLD 계약을 유지한다. 예측만 있는 박스와 오래된 관측으로 새 이동 목표를 생성하지 않는다. 마지막 목표로 계속 접근하는 것과 마지막 출력 명령을 HOLD하는 것을 구분한다. PING이나 중복 패킷으로 모션 watchdog을 무력화하지 않는다.

현재 시야에서 새 관측이 나타나야 ACQUIRE/TRACK으로 돌아간다. 시야 밖에서 어디로 갔는지 알아서 찾는다고 보장하지 않는다. 통신/카메라 장애 뒤에는 기존 명시적 재ARM 규칙을 지킨다.

HOLD는 물리적 즉시 정지나 전원 차단을 의미하지 않는다. 기존 `docs/02_serial_protocol.md`의 계약을 재사용하고 필요 없는 신규 명령·프로토콜 버전 변경을 피한다.

## 6. 전원·카메라·레이저

추가 축과 카메라를 넣지 않으므로 추가 전원 분배 설계도 이번 작업에 넣지 않는다. 기존 외부 서보 전원·공통 GND 원칙을 유지하고 두 축 동시 운용의 전압 강하·발열·리셋·접점 상태를 시험한다. 기존 장치가 실제로 충분한지는 시험 전 확정하지 않는다.

1080p60은 요청할 입력 모드이며 실제 입력 FPS, 모델 처리 FPS, 호스트 지연은 따로 기록한다. 조명·노출·블러·케이블·프레임 누적은 기존 검사 항목을 유지한다. 하드웨어 고정이 성능 부족이나 배선 문제를 무시하라는 뜻은 아니다. 안전한 운용이 불가능한 실물 문제가 나오면 기록하고 사용자에게 올린다.

레이저는 원래 설계의 후속 범위 그대로 둔다. 이번 보완에는 레이저 구동, 조준 좌표 보정 코드, 거리별 자동 조준을 추가하지 않는다.

## 7. CI / 리뷰 / 실물 시험 — SC01–SC08은 런타임 구현 전 계획

| ID | 자동 검증의 기대 결과 |
|---|---|
| SC01 | 깊이 입력이나 두 번째 카메라 없이 모의 단일 카메라 추종 경로 실행 |
| SC02 | 팬·틸트 각 경계와 잘못된 입력에서 허용 밖 구동 명령이 나오지 않음 |
| SC03 | 경계 바깥 오차가 지속돼도 내부 목표가 누적되지 않음 |
| SC04 | 안전한 안쪽 목표로 바뀌면 상태에 맞게 복귀하며 큰 점프 없음 |
| SC05 | 검출 유효지만 제어 제한인 경우와 관측 소실인 경우가 구분됨 |
| SC06 | 오래된 프레임·예측만 있는 타깃·연결 장애 시 기존 HOLD/구동 잠금 유지 |
| SC07 | 재연결·미보정·dry-run에서 실물 구동이 자동 활성화되지 않음 |
| SC08 | 거리·실제 각도·실제 60FPS를 미측정 상태에서 측정값으로 보고하지 않음 |

기존 테스트를 삭제·skip하거나 assertion을 약화해 통과시키지 않는다. 확장 기능용 테스트가 이미 있다면 현재 승인 범위와 대조하여 유지·격리·제외 근거를 명시하고 자동 삭제하지 않는다.

실물 확인: 축 방향·간섭·케이블 당김, 실제 FPS·지연, 지정 드론 검출 성능, 실제 추종, 전압 강하. CI는 이를 대신 검증했다고 보고할 수 없다. 안전한 장치 지지와 기존 승인 절차로 시험하며 무리한 끝단·머리 위 통과를 테스트한다는 이유로 강제로 구동하지 않는다.

### 성능 평가를 약화하지 않는 규칙

현재 확정된 정량 목표를 유지한다. 시험 영역은 통합시험 전에 고정한다. 그 영역 안에서 발생한 놓침·프레임 드롭·추종 실패는 실패로 기록한다. 시스템이 못 따라갔다는 이유로 나중에 “영역 밖”으로 재분류하지 않는다. 계획된 영역 밖 시험은 별도의 제한동작 시험으로 보고한다. 안전하게 HOLD한 것은 안전 동작 성공이지 추종 성공은 아니다.

기존 승인 문서에서 머리 위 무중단 추종이 정말 필수였는지 현재 저장소에서 발견하면 숨기지 말고 요구사항 충돌로 보고한다. 첨부 v1.0에서는 해당 보장을 확인하지 못했다.

## 8. 문서 적용과 진행 중 작업 보호

현재 Git 상태·미커밋 변경·진행 중 자동 작업부터 확인한다. 기존 사용자 변경, Codex 구현, CI·스킬을 보존한다. 재클론·전체 덮어쓰기·강제 reset·무관한 라이브러리 교체는 하지 않는다.

우선 최신 결정 기록에 이번 하드웨어 확정과 보완 방향을 기록하고, 설계서의 범위/제어/시험 부분을 동기화한다. 필요하면 본 파일을 새 보완문서로 추가하되 단독 문서만 남겨 상위 문서와 모순을 방치하지 않는다.

갱신 대상 예시:
- `docs/05_decisions.md`: 원래 하드웨어 유지, 거리·추가 축 보류, 보완 기준.
- `docs/01_system_design.md`: 운용 영역, 경계 제한, 머리 위 추종 보장 제외.
- `docs/03_dataset_and_evaluation.md`: 시험영역 사전 고정과 실패 집계 원칙.
- `docs/04_implementation_plan.md`: 필요한 보완 작업만 추가.
- `AGENTS.md`, 현재 리뷰 스킬·프롬프트: 승인 범위 대조, 거리/3축 미구현을 결함으로 오인하지 않기, 안전 누락은 계속 지적.
- 기존 설정/테스트: 이미 있는 키·모듈을 재사용. DOCX는 Markdown 기준이 확정된 뒤 재생성하거나 구버전 스냅샷으로 명시.

자동화는 이후 대화에서 별도로 확장된 분야다. 초기 v1.0의 “자동화 미정” 문구로 현재 승인된 CI·독립 리뷰·자동 수정 정책을 되돌리지 않는다. 이 보완을 근거로 Secret·권한·비용·병합 정책을 확대하거나 자기 정책 변경을 자체 승인하지 않는다.

상위 설계·결정·평가·개발 계획·작업/리뷰 지침을 함께 갱신한다. DOCX와 기존
PACKAGE_SHA256.json은 v1.0 배포 스냅샷으로 보존한다. 반입 원본은 사용자 요청에 따라
통합 검증 후 폴더를 삭제하며, 삭제 전에 로컬 artifacts에 회수용 ZIP을 보존하고 바이트를 대조한다.
